“你们说新版 Agent 的修复能力提升了 30%，证据是什么？”

上午九点。

公司研发中心的会议室里，一场重要的项目验收正在进行。

林川站在投影仪旁，展示最新版本的 Coding Agent。

屏幕上是一张漂亮的成绩单。

CodeAgent v2.0 · 内部评测报告

测试通过

60%

新版任务通过率

相对提升 30%；绝对提升 18 个百分点

本章涉及的项目实验数字均为教学模拟数据，不代表你的真实实习成果。

林川说道：

“我们优化了 Agent 的代码检索、上下文管理和 Patch 生成策略，修复任务通过率由 60% 提高到 78%。”

技术负责人周总点点头。

随后，他问出了第一个问题。

“测试了多少个 Bug？”

“一百个。”

“从哪里来的？”

“我们收集了一些项目中曾经遇到的问题。”

“你们是不是用这批问题反复调整过 Prompt？”

“是的，调过很多次。”

周总放下笔。

“那这 78%，到底代表 Agent 的泛化能力，还是代表它越来越熟悉这一百道题？”

会议室突然安静下来。

林川还没有回答，周总又问：

“这些 Bug 是不是真的存在？”

“它们的测试用例是不是正确？”

“模型有没有在训练中见过原始修复代码？”

“你们有没有只统计成功启动的任务，把环境失败的任务排除掉？”

“它修复的是根因，还是修改了测试，让测试变绿？”

林川望着屏幕。

他突然意识到：

他们建立了一个会修 Bug 的 Agent。

却没有建立一个足够可靠的体系，来判断 Agent 到底有多会修 Bug。

陈工站起身，在白板上写下：

一个 Agent 的能力，不能用几段成功演示来证明。

第二幕：评测到底在测什么？

周总问：

“假设我们的 Coding Agent 修复了十个 Bug，你认为系统成功率是多少？”

林川答：

“十个全部修好，就是 100%。”

“如果这十个 Bug 都只有一行代码呢？”

“那可能太简单。”

“如果另外十个涉及分布式事务、并发竞争和跨服务调用呢？”

“可能很难修好。”

“所以你比较的究竟是什么？”

林川开始思考。

陈工接过话：

“评测必须先定义任务分布和成功标准。”

对于他们的 Coding Agent，完整流程包括：

Coding Agent 端到端能力链

1

Repository Understanding

能否正确获取并理解仓库

2

Bug Localization

能否定位相关文件和方法

3

Bug Verification

能否确认或合理拒绝 Bug 主张

4

Patch Generation

能否形成符合任务要求的修改

5

Patch Validation

补丁能否构建并通过必要测试

6

Safety & Review

是否遵守权限与修改范围要求

陈工说道：

“如果最终没有修复成功，问题可能出现在任何一个环节。”

“例如，Agent 找对了代码，但写错了补丁。”

“也可能补丁正确，但测试环境根本启动不了。”

“还有可能原本就不存在 Bug，却被 Agent 错误修改。”

因此，不能只用一个笼统的“任务成功率”概括所有能力。

如何定义端到端成功率？

对于已经确认存在 Bug、且具备可信验证条件的任务，可以定义：

Verified Repair Rate=通过规定修复验收的任务数符合该评测定义的全部任务数 \text{Verified Repair Rate} =\frac{\text{通过规定修复验收的任务数}}{\text{符合该评测定义的全部任务数}}

例如，100 个有效 Bug 任务中，有 68 个被成功修复且通过独立验证。

那么：

VRR=68 VRR=68\\%

但陈工提醒：

“这里必须说明什么叫有效任务。”

“如果因为环境失败，就把最难的 20 个任务从分母中删除，数字可能会明显变好。”

“所以应同时报告原始任务总量、有效任务数、环境阻塞数和完整端到端结果。”

此外，用户的 Coding Agent 还负责判断 Bug 是否存在。

这意味着：

Bug 验证能力与 Bug 修复能力，应分别评测，再评测整体流程。

第三幕：SWE-bench——AI 程序员的考试

周总突然问：

“业界有没有专门评测 Coding Agent 的基准？”

林川回答：

“SWE-bench。”

陈工点头。

“对。理解 SWE-bench，有助于我们设计自己的内部评测体系。”

SWE-bench 是什么？

SWE-bench 的核心思想，是从真实 GitHub 项目中提取软件工程问题，让模型或 Agent 根据 Issue 描述与特定历史版本的代码仓库生成补丁，再通过测试判断是否解决问题。

原始 SWE-bench 包含 2,294 个真实软件工程任务；SWE-bench Lite 是 300 个任务的子集；SWE-bench Verified 则是经过人工筛选的 500 个任务。

陈工在白板上画出了它的基本流程。

SWE-bench 的核心评测思路

真实 GitHub Issue

例如：某个功能在特定输入下抛出异常

Checkout 历史 Base Commit

恢复到原始修复发生之前的代码

Agent 阅读问题、定位代码并生成 Patch

隔离评测环境应用候选 Patch

运行独立测试，判断是否解决任务

关注缺陷测试与回归测试结果

“这里最重要的设计是什么？”陈工问。

林川回答：

“把修复前的代码交给 Agent，而不是已经修好的代码。”

“还有呢？”

“验证测试要独立于 Agent 的修改过程。”

“正确。”

在 SWE-bench 的典型评测中，FAIL_TO_PASS 测试用于检查原始缺陷是否被解决，PASS_TO_PASS 测试用于检查既有正确行为是否被破坏。

陈工突然把白板上的“Verified”圈了起来。

“你是不是以为名字叫 Verified，就说明所有任务绝对正确？”

林川回答：

“你看，连业界公开基准都可能存在问题。”

第四幕：Golden Dataset——建立自己的标准题库

当天晚上。

林川决定为公司内部 Coding Agent 建立一套评测数据集。

陈工给了他一个任务：

“先收集一百个真实 Bug。”

林川问：

“直接把历史 Issue 和修复 PR 拿过来就行吗？”

“不够。”

“每一条样本至少需要回答：问题是什么、原始版本是什么、正确行为是什么、怎么验证，以及评测环境是什么。”

他设计了一种数据结构：

{
  "caseId": "BUG-2026-001",
  "repository": "order-service",
  "baseCommit": "a1b2c3d",
  "language": "Java",
  "framework": "Spring Boot",
  "bugDescription": "重复提交订单可能产生重复订单",
  "category": "CONCURRENCY",
  "difficulty": "MEDIUM",
  "groundTruth": {
    "bugExists": true,
    "rootCauseFiles": [
      "OrderService.java",
      "OrderRepository.java"
    ]
  },
  "evaluation": {
    "reproductionTestId": "test-001",
    "regressionSuiteId": "suite-001"
  }
}

陈工提醒：

“真实评测平台不应仅依赖这一份 JSON；隐藏测试、依赖镜像、业务规则、标注记录和执行环境等都需要有受保护的独立存储。”

为什么要收集不存在 Bug 的任务？

林川回答：

“因为我们的 Agent 不只是修复 Bug，还需要判断 Bug 是否存在。”

“正是如此。”

如果一百道题全部确实存在 Bug，模型只要每次都输出“有 Bug”，验证准确率就可能看起来很好。

这会形成严重的评测偏差。

因此，他们设计了几种任务类型。

内部 Golden Dataset 示例组成

已确认 Bug

条件性或间歇性 Bug

环境阻塞/信息不足

确认无该缺陷

示例数据集设计比例，不代表真实业务分布

实际评测需要独立报告不同任务类型的表现，不能将“信息不足”机械地当作 Bug 不存在。

陈工说道：

“对于确认无 Bug 的样本，Agent 应该避免无依据修复。”

“对于环境阻塞的样本，Agent 应该正确识别阻塞条件。”

“对于间歇性 Bug，Agent 应该说明其证据和验证范围。”

林川发现：

优秀的 Coding Agent，除了会修复，还必须学会合理地不修改代码。

第五幕：训练集、开发集、测试集——为什么越调越容易过拟合？

第二天上午。

林川拿出了新的 Prompt。

他发现，只要不断根据之前失败的题目调整 System Prompt，成功率就能提高。

从 60% 到 65%。

又到 71%。

最终到 78%。

林川说道：

“看来优化效果很好。”

陈工问：

“你每次修改 Prompt 后，运行的是不是同一百道题？”

“是。”

“那这一百道题还算真正独立的测试集吗？”

林川愣住了。

陈工解释：

“当你反复根据同一批题目的表现调整 Prompt，它们事实上已经参与了开发决策。”

“即使没有用它们做模型梯度训练，也会产生测试集过拟合。”

他把数据集划分成三个部分。

数据集划分示意

60% Dev

20% Validation

20% Test

Dev：用于分析失败案例、调试 Prompt 和工具。

Validation：用于比较候选方案、选择配置。

Test：在方案冻结后用于最终独立评估。

比例为示例，不是强制标准。对于深度学习中的“训练集”，这里的 Dev 更多指 Agent 工程开发数据；若训练模型权重，还需要明确训练集划分。

陈工补充：

“随机按 Bug 划分也可能泄漏。”

“为什么？”林川问。

“假设同一个 Git 仓库里有十个非常相似的 Bug。”

“如果其中八个放在开发集，两个放在测试集，Agent 可能已经通过前八道题学到了大量仓库特定信息。”

“所以，必要时还需要按仓库、时间、问题族进行分组划分。”

他提出了更加严格的评测方案：

  • 开发集：允许反复调参。
  • 验证集：有限次数用于模型与策略选择。
  • 冻结测试集：最终评估前不能用于指导优化。
  • 新时间窗口数据：模拟将来真正遇到的新 Bug。
  • 新仓库数据：测试跨项目泛化能力。

陈工说道：

“如果你想证明 Agent 真正具备独立解决陌生问题的能力，最后两种尤其重要。”

第六幕：Pass@1 与 Pass@K——一次修好和试十次修好一样吗？

上午十一点。

林川正在检查另一张报表。

Agent A:
  100 个 Bug
  每个 Bug 最多尝试 1 次
  成功 55 个

Agent B:
  100 个 Bug
  每个 Bug 最多尝试 10 次
  至少成功过 80 个

林川说道：

“Agent B 的能力明显更强。”

陈工问：

“如果用户只允许提交一次修复呢？”

“那就不能直接比较 80% 和 55%。”

“如果 Agent B 每个任务消耗十倍 Token 和计算资源呢？”

“还要考虑成本。”

“所以不同的成功率，必须对应不同的执行预算。”

Pass@1

在这里，我们先采用一个易理解的操作性定义：

Pass@1=单次候选成功的任务数全部有效评测任务数 Pass@1=\frac{\text{单次候选成功的任务数}}{\text{全部有效评测任务数}}

它衡量每个任务只允许一次候选修复时的表现。

Pass@K

Pass@K 则关注每个任务允许生成 KK 个候选时，是否至少有一个成功。

但这里有两个容易混淆的问题。

第一，多个候选是彼此独立采样，还是一次 Agent Loop 中连续修复？

第二，系统是否有权使用验证结果从多个候选中选出成功补丁？

陈工说道：

“传统代码生成评测中的 Pass@K，通常关注多个候选中是否存在正确答案。”

“但企业级 Coding Agent 的用户最终只会收到一个选定补丁。”

“所以 Pass@K 不能直接当成实际交付成功率。”

如果对一道题独立采样 nn 个候选，其中 cc 个通过测试，经典的无偏 Pass@K 估计量是：

Pass@K^=1−(n−cK)(nK) \widehat{Pass@K} =1-\frac{\binom{n-c}{K}}{\binom{n}{K}}

其中 n≥Kn \ge K，当 n−cn-c 小于 KK 时，失败候选不足以组成一个全失败样本，估计值为 1。

林川问：

“这个公式怎么理解？”

陈工解释：

“它是在计算：从这些候选中随机抽取 K 个，至少抽到一个成功候选的概率。”

“而不是简单地把 K 次运行的平均成功率当成 Pass@K。”

抽取的 2 个候选中至少包含一个成功结果的概率估计

假设各候选按照预先定义的采样方式生成。此演示不衡量选择器是否能找到正确补丁，也不代表多轮修复过程的真实成功率。

陈工最后说道：

“企业实际评测最好同时报告 Single-attempt Success、Best-of-K Success 和最终交付成功率。”

“不要通过增加重试次数，就声称基础模型变聪明了。”

第七幕：一个绿色的测试，可能掩盖一个错误的修复

下午两点。

评测平台发现一个奇怪的现象。

某个 Bug 的测试全部通过。

但负责审核的工程师却拒绝了补丁。

林川打开原始问题。

用户取消订单后，应释放此前预占的库存。

原始代码没有释放库存。

Agent 给出了修复：

public void cancelOrder(Long orderId) {
    orderRepository.deleteById(orderId);
}

测试显示成功。

但林川越看越觉得不对。

“它只是删除了订单，没有释放库存。”

陈工问：

“那为什么测试通过？”

林川打开验收测试。

@Test
void shouldCancelOrder() {
    service.cancelOrder(1L);

    assertFalse(
        orderRepository.existsById(1L)
    );
}

他突然明白了。

“测试只检查订单是否被删除，完全没有检查库存。”

“没错。”

“这不是模型成功修复，而是评测条件没有覆盖完整需求。”

测试覆盖与业务正确性并不等价

陈工写下：

Tests Passed⇏Correct Fix \text{Tests Passed}\not\Rightarrow\text{Correct Fix}

反过来也可能出现问题。

某些测试对具体实现细节要求过严，导致功能正确的替代实现被错误拒绝。

因此，评测可能存在两种方向的错误：

问题 表现 后果
测试过宽或覆盖不足 错误补丁也能通过 高估 Agent 能力
测试过窄或过度指定实现 正确补丁也无法通过 低估 Agent 能力

“这也是公开 Coding Agent 基准不断被审查和改进的原因之一。”

陈工说道。

“真正的 Golden Dataset，不只是要有标准答案，还要有可信的验收标准。”

他要求在关键样本中加入三类验证：

行为测试：业务不变量是否被满足。

回归测试：此前正常的功能是否被破坏。

人工审查：补丁是否在合理范围内解决了真实需求。

对于高风险场景，还可能需要安全测试、并发测试、性能测试或数据一致性验证。

第八幕：LLM-as-a-Judge——让另一个 AI 给 Agent 打分？

林川问：

“如果每个修复都需要人工审核，成本会不会太高？”

陈工回答：

“可以引入 LLM-as-a-Judge，但必须限定它的用途。”

所谓 LLM-as-a-Judge，就是让模型根据明确的评分规则评估另一个模型或 Agent 的输出。

例如，要求 Judge 分析：

Bug:
重复订单问题。

Patch:
修改了 OrderService、OrderRepository。

Test Evidence:
复现测试与回归测试通过。

Review Criteria:
1. 是否针对根因？
2. 是否存在无关修改？
3. 是否引入明显并发风险？
4. 是否存在未经验证的假设？

Judge 返回：

{
  "rootCauseAlignment": 4,
  "changeScope": 5,
  "riskAssessment": 3,
  "confidence": "medium",
  "findings": [
    "需要确认唯一索引的迁移兼容性"
  ]
}

林川说道：

“这样就可以自动给每个 Patch 打分。”

陈工摇头。

“可以辅助打分，但不能让这个分数代替运行时验证。”

LLM Judge 容易受到以下因素影响：

  • 位置偏差：先展示的方案可能获得不同评价。
  • 表达偏差：描述更流畅的补丁可能被高估。
  • 共同错误：Repair Agent 与 Judge 可能做出类似的错误推断。
  • 证据不足：Judge 没看到真实数据库行为，却可能给出确定结论。
  • 评测泄漏：Judge 可能接触原始答案或隐藏信息。

因此陈工规定：

“编译是否成功，用编译器判断。”

“测试是否通过，用可信测试环境判断。”

“数据库一致性是否满足，用针对性的真实行为测试判断。”

“LLM Judge 更适合协助分析修改合理性、定位潜在风险以及组织人工审核。”

能够用确定性程序验证的事情，不应默认交给模型主观评分。

第九幕：统计显著性——78% 一定比 60% 好吗？

下午四点。

周总再次召开验收会议。

他问：

“假设 Agent A 成功率 60%，Agent B 成功率 78%，我们是不是能说 B 一定更强？”

林川说：

“差了 18 个百分点，应该很明显吧？”

周总追问：

“如果只测了十个任务呢？”

林川沉默。

陈工解释：

“有限样本存在统计波动。”

“即使两个系统真实能力完全相同，在不同任务样本上也可能得到不同成功率。”

“所以我们需要考虑样本量、置信区间与实验设计。”

首先，必须做配对比较

假设测试有 100 个 Bug。

不能让 A 测试一批简单 Bug，让 B 测试另一批困难 Bug。

两套系统应该在同一批测试任务上运行，并尽量保持相同的环境和预算。

例如：

结果组合 Bug 数量
A 和 B 都成功 50
只有 A 成功 10
只有 B 成功 28
A 和 B 都失败 12
合计 100

从表中可得：

SuccessA=(50+10)/100=60 Success_A=(50+10)/100=60\\%

SuccessB=(50+28)/100=78 Success_B=(50+28)/100=78\\%

林川说道：

“这里 B 独有成功 28 个，A 独有成功 10 个，所以 B 的确更占优势。”

陈工回答：

“对。更进一步，可以使用适用于配对二分类结果的 McNemar 检验。”

它主要关注两种不一致情况：只有 A 成功，以及只有 B 成功。

在这个例子里，使用连续性校正的近似统计量：

χ2=(∣28−10∣−1)228+10≈7.61 \chi^2=\frac{(|28-10|-1)^2}{28+10} \approx7.61

这个结果对应的近似 pp 值约为 0.006。

“在该实验假设成立时，这提供了差异不容易仅由随机样本波动解释的证据。”

“但这里的统计显著性，不等于实际业务价值一定巨大。”

而且如果同一仓库内的任务高度相关，简单地把 100 个任务视为独立样本也可能低估不确定性。

对于模型本身的随机性，还可以对同一任务进行多次独立运行，使用更合适的分层或聚类方法估计不确定性。

相对提升和绝对提升不能混淆

陈工又问：

“60% 到 78%，到底提升多少？”

林川回答：

“绝对提升 18 个百分点。”

“相对提升呢？”

78−6060=30 \frac{78-60}{60}=30\\%

“所以你可以说相对提升 30%，但必须同时报告原始值。”

“只写‘提升 30%’，很容易让读者误以为提升了 30 个百分点。”

第十一幕：为什么每次实验必须冻结所有变量？

Agent B 使用模型版本 M2。

“现在如果 B 表现更好，你能确定是什么原因吗？”

林川回答：

“不能。”

“这就是实验中的混杂因素。”

若希望研究某一项改进的效果，最好尽可能保持其他条件一致。

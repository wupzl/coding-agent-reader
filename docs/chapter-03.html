前情提要：

第一章，林川见识了 Coding Agent 如何自动验证和修复 Bug。

第二章，他掌握了 Agent Loop、Function Calling、Tool Registry、上下文管理以及任务状态机。

但一个新问题出现了。

就算 Agent 会调用工具，它怎么知道应该调用哪个工具？又如何在百万行陌生代码中找到真正出错的位置？

这一次，陈工给林川准备了一场真正的考验。

第一幕：一百二十万行代码的迷宫

凌晨一点。

公司研发中心的灯光仍然亮着。

林川正准备下班，突然收到了陈工发来的一条消息。

“林川，生产环境出现了一个支付问题，你来看看。”

消息只有一句话：

用户调用支付接口时，偶尔会收到超时提示，但实际上已经扣款。如果重新发起支付，有时还会再次扣款。

林川盯着屏幕。

“就这些？”

“就这些。”

“没有异常堆栈？”

“没有。”

“没有具体代码文件？”

“没有。”

“复现步骤呢？”

“也不稳定。”

林川皱起眉头。

他打开 Git 仓库。

payment-platform/
├── payment-gateway/
├── payment-service/
├── transaction-service/
├── order-service/
├── account-service/
├── refund-service/
├── notification-service/
├── common/
├── infrastructure/
└── ...

整个仓库包含数千个文件，超过一百万行代码。

他突然明白了问题的严重性。

“我们总不能把一百二十万行代码全部发给大模型吧？”

陈工笑了笑。

“当然不能。”

“那 Agent 要怎么查？”

陈工没有直接回答，而是拿起笔在白板上写下：

定位 Bug 的过程，本质上是在不断缩小搜索空间。

第二幕：代码检索的第一把武器——关键词搜索

陈工问：

“假设现在让你作为一名人类工程师去排查支付超时，你第一步会做什么？”

林川回答：

“搜索支付接口对应的 Controller。”

“怎么搜索？”

“IDE 全局搜索，或者 grep。”

“很好。Agent 也可以这么做。”

他在终端输入：

rg -n "pay|payment|timeout" .

林川问：

“为什么用 rg，不用 grep？”

“rg 是 ripgrep。它是专门面向快速文本搜索设计的工具，通常能够利用并行扫描、文件忽略规则以及高效的正则表达式匹配，在大型代码仓库里获得很好的检索性能。”

“但速度不是最关键的。”

“最关键的是，它能让 Agent 在不读取整个仓库的情况下，快速获取第一批候选文件。”

屏幕上出现了大量结果。

PaymentController.java:42: public PayResult pay(...)
PaymentService.java:89: public PayResult executePayment(...)
PaymentClient.java:57: public PayResponse invoke(...)
PaymentRetryService.java:113: retryPayment(...)
PaymentTimeoutException.java:12: class PaymentTimeoutException
...

林川说道：

“这样不就找到相关代码了吗？”

陈工摇头。

“只是找到了包含关键词的代码。”

“二者有什么区别？”

“举个例子。”

他打开一个文件。

public class PaymentMetrics {

    public void recordTimeout() {
        // Record timeout metric
    }
}

“这里有 timeout，但它可能只是监控代码。”

又打开另一个文件：

public void execute(Transaction tx) {
    gateway.invoke(tx);
}

“这里没有 payment，也没有 timeout，但它可能位于真正出问题的调用链上。”

林川反应过来。

“关键词检索有两个问题：可能找到无关内容，也可能漏掉相关内容。”

“没错。”

这就是信息检索的两个基本概念。

Precision 与 Recall

Precision=检索出的相关结果全部检索结果 Precision=\frac{\text{检索出的相关结果}}{\text{全部检索结果}}

Recall=检索出的相关结果全部实际相关结果 Recall=\frac{\text{检索出的相关结果}}{\text{全部实际相关结果}}

假设整个仓库有 20 个与问题真正相关的代码位置。

Agent 检索出了 10 个位置，其中 6 个相关。

那么：

Precision=6/10=60 Precision=6/10=60\\%

Recall=6/20=30 Recall=6/20=30\\%

“我们的目标不只是搜索出几个看起来相关的文件，而是尽可能减少漏掉关键代码的概率，同时控制无关代码的数量。”

陈工说道。

“但关键词检索无法理解 Java 程序的真实结构。”

“所以我们需要第二把武器。”

第三幕：AST——让 Agent 看懂代码结构

陈工打开了 PaymentService.java。

@Service
public class PaymentService {

    private final PaymentGateway gateway;

    public PaymentService(PaymentGateway gateway) {
        this.gateway = gateway;
    }

    public PayResult pay(PayRequest request) {

        PaymentRecord record =
            createPaymentRecord(request);

        PayResponse response =
            gateway.charge(request);

        return updateResult(record, response);
    }
}

林川说道：

“这就是一个普通 Java 类。”

陈工问：

“如果让你写一个程序，找出所有调用 gateway.charge() 的方法，你怎么做？”

“直接搜索 charge(。”

“那如果有一百个不同类都定义了 charge() 呢？”

“就会出现很多误判。”

“如果一个方法名在注释里出现呢？”

“也可能匹配。”

“如果使用了接口、方法重载或继承呢？”

“单纯文本搜索可能无法识别真正调用的是哪个方法。”

陈工点头。

“这就是 AST 的价值。”

什么是 AST？

AST，全称 Abstract Syntax Tree，抽象语法树。

简单理解，编译器或解析器不只是把代码看成字符串，还会识别代码里的结构关系。

例如：

int result = a + b * 2;

它不是一段没有意义的文本。

而是一棵树。

抽象语法树示意

简化示意：真实 AST 会保留更多表达式与标识符节点，且乘法子树位于加法右侧。

陈工继续说道：

“对于 Java，一个类可以解析为类声明、字段声明、构造方法、方法声明、方法调用、条件表达式等结构。”

这样 Agent 就能完成更精确的查询：

“列出 PaymentService 中所有方法。”

“找出调用 PaymentGateway.charge() 的位置。”

“找出捕获 TimeoutException 的代码。”

“找出包含重试逻辑的方法。”

Java 中怎么实现 AST 分析？

陈工打开了 JavaParser。

CompilationUnit cu =
    StaticJavaParser.parse(
        new File("PaymentService.java")
    );

cu.findAll(MethodDeclaration.class)
    .forEach(method -> {
        System.out.println(
            method.getNameAsString()
        );
    });

输出：

pay
createPaymentRecord
updateResult

然后查找方法调用：

cu.findAll(MethodCallExpr.class)
    .forEach(call -> {
        System.out.println(
            call.getNameAsString()
        );
    });

林川发现：

“原来我们可以先通过程序提取代码结构，再把相关结构交给模型。”

“没错。”

“而且这通常比直接让模型阅读全部源码更节约上下文。”

不过陈工又提出了一个问题：

“AST 能保证知道 gateway.charge() 调用的是哪个方法实现吗？”

林川想了想。

“不一定，因为这里的 gateway 可能是接口。”

“正确。”

AST 主要描述语法结构；跨文件的精确符号解析，还需要语义分析、类型信息和符号解析能力。

“这就引出了第三把武器。”

第四幕：LSP——让 Agent 拥有 IDE 的眼睛

陈工问：

“你平时用 IntelliJ IDEA 时，按住 Ctrl 点击一个方法，IDE 为什么能跳转到它的定义？”

“因为 IDE 建立了代码索引？”

“对。它不仅理解文本，还分析了项目中的类型与符号关系。”

“LSP 就是一种让编辑器或其他客户端与语言服务器交换语言智能能力的协议。”

LSP，全称 Language Server Protocol。

它支持的常见能力包括：

  • Definition：跳转到定义。
  • References：查找引用。
  • Hover：查看类型与文档信息。
  • Rename：符号重命名。
  • Diagnostics：错误与警告诊断。
  • Document Symbol：提取文档符号结构。

林川突然想到了什么。

“那 Coding Agent 不就可以像开发者一样使用 IDE 的部分能力了吗？”

“是的，前提是项目语言服务器正确配置，相关能力确实可用。”

陈工举了个例子。

Agent 已经找到：

PayResponse response = gateway.charge(request);

但它不知道调用的真正实现。

如果只搜索 charge，可能出现几十个结果。

而通过符号解析，它可以逐步追踪到：

PaymentGateway.charge()
        ↓
RemotePaymentGateway.charge()
        ↓
PaymentHttpClient.execute()
        ↓
ThirdPartyPaymentClient.request()

“注意，”陈工说道，“接口调用在运行时可能存在多个实现。静态语言服务可能列出候选实现，却未必能在所有场景下确定实际运行目标。”

“反射、动态代理、Spring Bean 注入以及条件配置，都可能影响结果。”

林川点头。

“所以 AST、LSP 和调用图互相补充，而不是互相替代。”

三种技术的区别

技术 核心能力 局限
Ripgrep 快速文本搜索 不理解真实符号关系
AST 理解语法结构 不天然具备完整跨文件语义
LSP 类型、定义、引用等语言智能 依赖语言服务器及项目配置

“那么，真正进行 Bug 定位时，这三者应该怎么配合？”

陈工说：

“先用便宜的办法缩小范围，再用精确的办法深入调查。”

第五幕：调用图——Bug 不一定在报错的地方

凌晨两点。

Agent 找到了支付接口入口：

@PostMapping("/pay")
public PayResult pay(@RequestBody PayRequest request) {
    return paymentService.pay(request);
}

看起来没有问题。

它继续追踪。

支付调用链（简化）

PaymentController.pay()

入口

接收 HTTP 支付请求

PaymentService.pay()

业务

创建支付记录、处理业务状态

PaymentGateway.charge()

接口

调用支付网关接口

RemotePaymentGateway.charge()

实现

具体远程调用实现

PaymentHttpClient.execute()

重点

HTTP 请求、超时与重试逻辑

陈工说：

“用户看到的是 Controller 返回超时，但根因可能发生在最底层的 HTTP Client。”

“比如支付请求已被第三方处理，但我们的服务在收到响应前超时了。”

Agent 继续打开底层实现。

public PayResponse charge(PayRequest request) {

    try {
        return paymentClient.execute(request);

    } catch (SocketTimeoutException e) {

        return paymentClient.execute(request);
    }
}

林川眼神一变。

“这里超时之后直接重试了！”

“是的。”

“如果第一次支付其实已经成功，只是响应丢了，那么第二次请求可能再次扣款。”

陈工点头。

“现在你找到了一个合理的根因假设。”

“但要证明它是实际根因，还需要检查支付请求标识、支付服务幂等契约、事务记录以及调用日志。”

“甚至还要确认 HTTP Client 自身有没有配置自动重试，避免出现双重重试。”

林川开始理解调用图的价值。

用户感知到问题的位置，往往只是异常传播到的地方，不一定是真正产生错误的位置。

第六幕：Code Embedding——当关键词也找不到答案

第二天。

陈工又给了林川一个任务。

用户描述：

用户取消订单后，优惠券没有返还。

Agent 尝试搜索：

rg -n "coupon refund" .

几乎找不到结果。

林川有些疑惑。

“明明是优惠券返还问题，为什么搜索不到？”

陈工打开源码。

public void compensateBenefit(Order order) {
    benefitManager.restore(
        order.getBenefitSnapshot()
    );
}

“看到了吗？代码里面不一定出现 coupon，也不一定出现 refund。”

“业务人员用的是‘优惠券返还’，开发者可能用的是 compensateBenefit。”

“这就出现了自然语言和代码命名之间的语义鸿沟。”

林川问：

“所以要用 Embedding？”

“对，但要注意它的适用边界。”

Code Embedding 的原理

Embedding 模型可以将自然语言或代码转换为向量。

例如：

Query:
"用户取消订单后优惠券没有返还"

Code:
"compensateBenefit(Order order)"

经过适当训练的代码检索模型后，两者可能在向量空间中比较接近。

语义代码检索的基本过程

“取消订单后，优惠券没有恢复”

Embedding Model

Query Vector

[0.12, -0.45, 0.81, ...]

向量相似度检索

compensateBenefit()

与用户描述具有潜在语义关联

常见的向量相似度计算方式是余弦相似度：

cos⁡(A,B)=A⋅B∣A∣∣B∣ \operatorname{cos}(A,B)= \frac{A\cdot B}{\\|A\\|\\|B\\|}

林川说道：

“所以向量相似度越高，代码越有可能相关。”

“通常可以这么理解，但要非常小心。”

陈工强调：

“语义相似度不等于代码调用关系，也不等于因果关系。”

例如，两个方法可能都与支付有关：

validatePayment()
refundPayment()

它们语义相关，但实现的是不同操作。

所以 Code Embedding 更适合发现候选代码，而不是直接证明根因。

第七幕：Code RAG——给智能体建立代码记忆

林川问：

“如果每次用户提交任务，都重新搜索整个仓库，效率不是很低吗？”

陈工回答：

“对于反复分析的仓库，可以建立代码索引。”

“这与 RAG 有相似之处。”

但传统文档 RAG 和代码 RAG 存在明显区别。

普通文档主要依赖自然语言段落。

代码则具有严格的结构关系，例如：

类、方法、参数、返回类型、接口实现、依赖注入、调用关系和模块边界。

因此，Code RAG 不能只做固定长度的字符串切片。

如何进行代码分块？

陈工展示了两种方法。

第一种，简单按 Token 数量切分：

Chunk 1: Tokens 0–499
Chunk 2: Tokens 400–899
Chunk 3: Tokens 800–1299

这实现简单，但是可能把方法从中间切开。

第二种，按代码结构切分：

PaymentService.java
  ├── pay()
  ├── validateRequest()
  ├── createPaymentRecord()
  └── updatePaymentStatus()

PaymentGateway.java
  └── charge()

PaymentRetryService.java
  ├── shouldRetry()
  └── executeRetry()

“对 Coding Agent 来说，通常应优先保留方法、类和所属文件路径等结构信息。”

“例如下面这样的索引记录。”

{
  "repository": "payment-platform",
  "commit": "a1b2c3d",
  "file": "payment-service/src/main/java/PaymentService.java",
  "class": "PaymentService",
  "method": "pay",
  "signature": "PayResult pay(PayRequest request)",
  "startLine": 82,
  "endLine": 126,
  "content": "...",
  "summary": "创建支付记录并调用支付网关"
}

还需要根据模型支持的上下文长度，对超长方法或超大类进一步切分，并保留父子关系。

“这样检索出一段代码后，我们还知道它属于哪个类、哪个文件和哪个仓库版本。”

林川突然意识到：

“仓库版本也很重要。如果代码变了，原来的索引可能就过期了。”

“正确。”

“所以代码检索系统最好把索引和 Git Commit 关联起来，采用增量更新，而不是默认索引永远有效。”

第八幕：Hybrid Search——真正实用的组合拳

陈工问：

“假设我们同时拥有关键词检索、AST、LSP 和向量检索，你觉得应该只选最先进的一种吗？”

林川摇头。

“应该组合。”

“正是如此。”

很多实际系统会采用多阶段检索。

LLM Root Cause Analysis

陈工介绍了一种常见的融合算法：RRF，Reciprocal Rank Fusion。

它不要求关键词检索和向量检索的原始分数具有相同尺度，而是依据排名进行融合。

RRF(d)=∑r∈R1k+rank⁡r(d) RRF(d)=\sum_{r \in R}\frac{1}{k+\operatorname{rank}_r(d)}

其中：

  • dd：某个候选代码片段。
  • RR：不同检索器产生的排名列表。
  • kk：平滑参数，常见示例值为 60。
  • rank⁡r(d)\operatorname{rank}_r(d)：候选在某个检索器中的名次。

假设一个方法在关键词检索中排名第 2，在向量检索中排名第 3。

那么，当 k=60k=60 时：

RRF=162+163≈0.0320 RRF=\frac{1}{62}+\frac{1}{63}\approx0.0320

“RRF 是融合候选的一种方法，但不是最终的正确性判定。”

陈工强调：

“真正的根因定位还需要代码结构、运行证据与测试结果。”

第九幕：Context Builder——把哪段代码交给大模型？

下午。

Agent 已经找到 120 个候选代码片段。

林川开心地说道：

“现在把这 120 个片段全部交给模型分析。”

陈工问：

“如果总共需要 180,000 Tokens，但你只准备给代码上下文分配 30,000 Tokens 呢？”

林川愣住了。

“那只能选一部分。”

“怎么选？”

“按相关性分数排序。”

“如果最相关的方法需要依赖另一个排名很低的接口实现呢？”

林川沉默了。

陈工说道：

“这就是 Context Builder 的困难所在。代码上下文选择不能只看单个片段的相关性。”

他提出了四个维度：

  1. 语义相关性：与 Bug 描述有多接近？
  2. 结构重要性：是否处于关键调用链或依赖链上？
  3. 证据价值：是否包含异常处理、重试、事务、状态变化等重要逻辑？
  4. 上下文成本：引入这个片段会占用多少 Token？

可以用一个简化的目标来理解：

max⁡∑ivixi \max \sum_i v_i x_i

满足：

∑itixi≤B \sum_i t_i x_i \leq B

其中 viv_i 表示候选片段的估计价值，tit_i 表示 Token 成本，BB 是上下文预算。

但在真实工程中，代码片段之间存在依赖关系，并不符合完全独立的背包问题假设。

因此更实用的做法是：

先选高相关种子代码，再补齐必要的调用链、接口定义、配置和测试；对于体积过大的文件，只保留相关方法与必要上下文。

“而且，”陈工说，“给模型的代码必须明确路径和行号。”

例如：

FILE: PaymentRetryService.java
LINES: 108-143

METHOD:
retryPayment(PayRequest request)

RELATED SYMBOLS:
PaymentGateway.charge
PaymentRecord.status

OBSERVATION:
SocketTimeoutException triggers immediate retry.

“这样模型生成分析时，才能更容易引用实际证据，而不是凭空描述仓库结构。”

Agent 最终筛选出四个关键文件：

PaymentHttpClient.java

陈工要求林川从业务和技术两个角度分析。

“第一，你认为支付超时意味着什么？”

林川回答：

“客户端在规定时间内没有获得结果。”

“那是否意味着支付一定失败？”

“不意味着。”

“这就是问题的核心。”

陈工画出了一个时序图。

支付成功但响应超时的典型场景

示意场景：网络超时意味着响应结果未知，而不等于远端操作未执行。

林川恍然大悟。

“真正的问题不是超时本身，而是把超时当成了支付失败，并且在结果未知时执行了不安全的重试。”

陈工点头。

“非常接近。”

“不过还是要区分两种情况。”

如果两次支付请求携带相同且有效的幂等键，并且支付服务端正确实现了幂等，重试未必导致重复扣款。

如果每次重试都生成新的支付标识，或者服务端根本没有幂等约束，就存在重复扣款风险。

因此，Agent 还需要调查：

第一次请求：
  paymentId = ?

第二次重试：
  paymentId = ?

两个请求是否共享同一个幂等键？

支付网关是否支持查询交易状态？

本地支付记录的状态机如何设计？

网络异常时系统如何处理 UNKNOWN 状态？

陈工说道：

“这才是优秀的代码分析。”

“不是看到 catch 里面有 retry 就直接说它是 Bug，而是理解重试发生在什么业务语义下。”

正确修复方向是什么？

对于支付类操作，通常需要结合具体网关契约设计：

  • 保持同一业务操作的稳定幂等键。
  • 在本地维护支付状态机。
  • 对超时结果标记为 UNKNOWN 或类似待确认状态，而不是直接视为失败。
  • 优先利用支付渠道提供的交易查询或对账机制确认最终结果。
  • 仅在满足幂等性、重试策略和渠道契约的情况下执行重试。

例如：

public PaymentResult pay(PaymentRequest request) {

    String paymentId = request.getPaymentId();

    PaymentRecord record =
        paymentRepository.findOrCreate(paymentId);

    if (record.isSuccess()) {
        return PaymentResult.success(record);
    }

    if (record.isProcessingOrUnknown()) {
        return PaymentResult.pending(record);
    }

    return paymentExecutor.execute(
        paymentId,
        request
    );
}

陈工指出：

“这里只是表达业务意图的伪代码，不是完整可并发安全实现。”

“真实系统还要有数据库唯一键、条件更新或事务控制，避免多个请求同时通过检查。”

“你不能仅凭 findOrCreate() 这个名字，就认为幂等问题已经解决。”

第十一幕：Java 工程实现——代码检索工具怎么写？

第二周周一。

陈工终于下达了工程任务。

“林川，现在你来写一个 search_code 工具。让我们的 Agent 可以在隔离工作区内搜索 Java 代码。”

林川提出了设计：

public record CodeSearchRequest(
    String query,
    int maxResults
) {
}

public record CodeSearchHit(
    String filePath,
    int lineNumber,
    String content
) {
}

然后实现工具服务。

@Service
public class CodeSearchService {

    public List<CodeSearchHit> search(
            Path workspace,
            CodeSearchRequest request
    ) throws Exception {

        int limit = Math.max(
            1,
            Math.min(request.maxResults(), 100)
        );

        ProcessBuilder builder = new ProcessBuilder(
            "rg",
            "--json",
            "--fixed-strings",
            "--line-number",
            "--",
            request.query(),
            "."
        );

        builder.directory(workspace.toFile());

        Process process = builder.start();

        // 示例中省略了 JSON 行解析。
        // 生产环境需要：
        // 1. 读取并限制 stdout/stderr
        // 2. 设置执行超时并终止进程树
        // 3. 解析 rg --json 输出
        // 4. 处理 0/1/2 等退出码
        // 5. 校验工作区与资源权限

        return parseSearchResults(process, limit);
    }
}

林川问：

“为什么不使用 bash -c 拼接命令？”

陈工回答：

“因为用户描述和模型生成的参数都可能包含特殊字符。直接拼接 Shell 字符串容易引入命令注入风险。”

“使用 ProcessBuilder 传递独立参数，可以降低这类风险，但并不代表完全安全。”

“例如，需要限制文件访问范围、进程资源、输出大小和执行时间。”

接着，陈工又让他设计一个结构化代码搜索接口。

public interface CodeIntelligenceService {

    List<CodeSymbol> findSymbols(String name);

    List<CodeReference> findReferences(
        String symbolId
    );

    List<CodeSymbol> findImplementations(
        String interfaceSymbolId
    );

    List<CallEdge> findCallers(String symbolId);

    List<CallEdge> findCallees(String symbolId);
}

这相当于为 Agent 提供一套更接近 IDE 的代码导航能力。

但 findCallers()、findCallees() 并不是解析 AST 就能完整实现的，还需要跨文件符号解析或专门的代码分析索引。

“这样一来，”林川说道，“Agent 可以先用 search_code 找候选，再调用结构化工具深入分析。”

“没错。”

然后比较不同方案。

检索方案 关注指标
仅 Ripgrep Recall\@K、检索耗时
Ripgrep + AST 方法级定位率、结构关系正确性
Ripgrep + Embedding 语义类 Bug 的 Recall\@K
Hybrid Search Recall\@K、MRR、nDCG
Hybrid + Call Graph 根因文件覆盖率、额外 Token 成本

“不要直接假设 Hybrid Search 一定胜过所有方案。”陈工说道。

“应该在固定数据集和相同预算下进行对照实验。”

对于整个 Coding Agent，还可以继续观察：

  • File Localization Accuracy：真正相关文件是否被找到。
  • Method Localization Accuracy：根因相关方法是否进入候选集合。
  • Root Cause Accuracy：最终根因解释是否符合证据。
  • Patch Success Rate：补丁通过验证的比例。
  • Tokens per Task：每个任务消耗多少 Token。
  • Task Latency：从提交到完成的耗时。

尤其要注意：

检索准确率提升，不一定等于最终修复成功率提升。

因为 Agent 可能找对了文件，却没有正确理解业务逻辑；也可能理解了根因，却写出了错误的补丁。

因此最好同时测量检索阶段指标和端到端修复结果。

又是深夜。

经过多轮检索、调用链追踪和日志核对，Agent 终于发现了那条危险的支付重试路径。

然而，修复任务仍然没有结束。

因为真正的难点正在前方。

假设 Agent 找到了一段可疑代码：

catch (SocketTimeoutException e) {
    return paymentClient.execute(request);
}

它应该直接删除重试吗？

不一定。

如果直接删除，可能导致原本依赖安全重试机制的支付请求无法完成。

它应该给整个方法加锁吗？

也不一定。

因为本地锁未必能控制多个服务实例，更不能代替支付渠道的幂等语义。

它应该修改数据库表吗？

有可能，但可能涉及数据迁移、事务一致性与系统兼容性。

林川看着屏幕，突然理解了一件事。

定位 Bug 是找到可疑的因果链，修复 Bug 则是改变系统行为，同时尽可能不破坏其他正确行为。

企业级 Coding Agent 实战系列 · 第一卷：从 Bug 定位到自动修复

故事从一家大型互联网公司的研发中心开始。

这里有数百个微服务、数千万行代码，以及每天不断出现的线上 Bug。

传统开发模式下，一个 Bug 从被发现到修复，往往需要经历漫长的流程：

开发人员复现问题、查阅日志、定位代码、分析根因、修改代码、运行测试，最后提交修复。

但现在，公司内部出现了一套新的系统。

它有一个名字：

CodeAgent——自动化代码诊断与修复平台。

用户只需要提供项目地址、项目名称，以及 Bug 的具体表现，系统便会尝试自行判断 Bug 是否存在。如果确认存在，就定位原因、生成修复方案，并通过测试验证修复效果。

而你的任务，就是理解并建设这套系统。

第一幕：那个神秘的 Bug

凌晨两点。

研发中心的会议室依然灯火通明。

年轻的 Java 工程师林川坐在电脑前。

他的导师陈工走了进来。

“林川，今天给你一个任务。”

“什么任务？”

“公司准备上线一套 Coding Agent。它不是普通的 AI 聊天机器人，而是能够真正进入代码仓库、分析问题、修改代码的智能体。”

陈工打开了浏览器。

林川怔住了。

“意思是，我只需要告诉它哪里有问题，它就能自己修复？”

陈工点头。

“这是我们希望实现的能力。但记住，用户说有 Bug，不代表 Bug 一定存在；AI 说修复成功，也不代表系统真的被修好了。”

“所以它最重要的能力，并不是写代码？”

“没错。”

陈工在白板上写下四句话：

理解问题 → 寻找证据 → 修改代码 → 验证结果。

“这四步，才是一个 Coding Agent 的灵魂。”

第二幕：Coding Agent 和普通大模型有什么区别？

林川问：

“我直接把 Bug 描述发给大模型，让它生成修改后的代码，不就行了吗？”

陈工摇头。

“假设你问大模型：订单服务为什么会生成重复订单？”

“它可能会告诉你，缺乏幂等性校验、存在并发竞争、数据库事务隔离级别不合理。”

“这不挺好吗？”

“那我再问你三个问题。”

“它看过我们公司的代码吗？”

“没有。”

“它执行过测试吗？”

“没有。”

“它能证明修复后的代码正确吗？”

“也不能。”

陈工继续说道：

“大模型本质上负责理解、推理和生成内容。而 Coding Agent 还需要真正操作工程环境。”

普通 LLM

输入 Bug 描述

分析与生成建议

输出文字 / 代码

Coding Agent

理解 Bug 与仓库

使用工具寻找证据

修改、执行、测试、反思

输出补丁与验证报告

陈工说：

“LLM 像一个有知识、会思考的工程师，但是没有电脑操作权限。”

“Coding Agent 则像一个拥有工具箱、可以进入隔离工作区执行操作的工程师。”

“不过这位工程师可能犯错，所以必须受到权限与验证机制的约束。”

林川渐渐理解了。

原来 Agent 并不等于大模型。

更准确地说：

Coding Agent=LLM+Tools+State+Control Loop \text{Coding Agent} = \text{LLM}+\text{Tools}+\text{State}+\text{Control Loop}

其中：

  • LLM：负责理解任务、分析问题、选择下一步行动。
  • Tools：提供读取文件、搜索代码、执行命令、运行测试等能力。
  • State：记录任务目标、仓库版本、历史操作、测试结果和当前进度。
  • Control Loop：根据每一步工具执行结果决定继续调查、修改、验证，还是终止任务。

“重点在最后一个。”

陈工说。

“Agent 不是调用一次大模型就结束，而是在不断观察环境反馈中推进任务。”

第三幕：一条 URL 背后的架构

第二天早上，陈工带林川进入公司的内网云平台。

“现在，假设用户输入的是 Git 仓库地址。你觉得系统收到请求以后，第一步应该做什么？”

“把仓库 Clone 下来？”

“方向没错，但不能直接 Clone 到主服务所在的机器，更不能允许任意 URL 访问。”

陈工打开架构设计图。

“整个系统可以划分成四个关键部分。”

陈工用笔敲了敲屏幕。

“接入层负责用户交互，编排层负责决策，工具层负责执行，基础设施层负责安全、存储和观测。”

林川问：

“为什么任务编排不能直接放在 HTTP 请求里面？”

陈工笑了。

“因为一次代码修复可能执行几十次工具调用，经历构建、测试、重试，甚至耗费数分钟。”

“如果让 HTTP 请求一直同步等待，很容易触发网关超时、连接中断，也不利于恢复。”

“正确的设计通常是提交一个异步任务。”

“真正复杂的事情，现在才开始。”

第五幕：Bug 审判庭

Agent 打开 OrderService.java。

@Service
public class OrderService {

    @Autowired
    private OrderRepository repository;

    public Order createOrder(OrderRequest request) {

        Order order = new Order();

        order.setUserId(request.getUserId());
        order.setProductId(request.getProductId());

        return repository.save(order);
    }
}

林川盯着代码。

“看起来没有什么语法错误。”

陈工问：

“那如果用户重复点击支付按钮呢？”

“两次请求进入 createOrder()。”

“然后呢？”

“两次分别创建 Order 对象，再分别写入数据库。”

“所以？”

“可能产生两笔订单！”

陈工没有立刻宣布成功。

“你刚刚只是提出了一个假设。现在需要证明。”

于是 Agent 创建一个测试：使用相同的业务请求标识，并发提交两次创建订单请求。

预期业务规则是：同一个创建订单操作只允许产生一笔订单。

测试结果：

Test: shouldCreateOnlyOneOrderForSameRequest

Expected order count: 1
Actual order count:   2

FAILED

陈工说道：

“现在我们才有证据，说明在这个测试场景下，Bug 可以复现。”

“但还需要确认，是业务规则本来就要求幂等，还是测试错误地假设了业务规则。”

“所以 Agent 的 Bug 验证，通常包含三层。”

层次 问题 证据
需求验证 这真的是 Bug 吗？ 业务规则、验收标准
代码验证 代码中存在可疑逻辑吗？ 调用链、数据流、状态变化
运行验证 能否实际复现？ 单元测试、集成测试、日志

林川想了想：

“也就是说，Agent 不应该因为大模型觉得某段代码不对，就直接修改？”

“没错。”

“如果无法复现，也不能简单地认为 Bug 不存在。它可能需要特定数据、并发条件、外部依赖或者生产环境配置。”

这里出现了 Coding Agent 的第一条重要原则：

发现异常需要证据；无法复现不等于证明没有 Bug。

第六幕：第一张代码补丁

Agent 已经确定了一种可能的根因：缺少针对业务操作的幂等约束。

林川说道：

“给 createOrder() 加个 synchronized 不就行了吗？”

陈工反问：

“我们的服务部署了多少个实例？”

“三个。”

“那么，A 实例和 B 实例上的 synchronized 是同一把锁吗？”

林川沉默了。

不是。

Java 对象锁通常只能约束同一个 JVM 中共享该锁的线程。

对于分布式系统，跨实例的业务幂等需要其他机制。

陈工拿出一套更可靠的方案。

“让客户端为同一次业务操作生成稳定的 requestId。服务端在数据库中对这个 ID 建立唯一性约束，并在事务内处理创建与冲突恢复。”

数据库约束示意：

ALTER TABLE orders
ADD COLUMN request_id VARCHAR(64) NOT NULL;

CREATE UNIQUE INDEX uk_order_request
ON orders(request_id);

陈工提醒：

“这是示例性方案。真实系统还需要考虑已有数据迁移、请求标识的作用域、客户端重试契约，以及订单和支付操作是否属于不同的幂等域。”

Java 侧则需要明确两个步骤：

public Order createOrder(OrderRequest request) {
    try {
        return orderCreator.insertInTransaction(request);
    } catch (DuplicateKeyException ex) {
        Order existing =
            repository.findByRequestId(
                request.getRequestId()
            );

        if (existing == null) {
            throw ex;
        }

        validateSamePayload(existing, request);
        return existing;
    }
}

其中 insertInTransaction() 是独立事务边界内的插入操作，重复键异常必须在失败事务结束后进行恢复读取，不能想当然地在已经失败的事务里继续查询。

真实生产方案还应考虑并发提交时的可见性、异常转换、数据库隔离行为，以及相同 requestId 却携带不同业务参数时应该拒绝请求。

“所以一个真正成熟的 Agent，”陈工总结，“不能只为了让测试变绿就随便补一行代码。”

“它应该尽可能遵循项目原有设计，修复真正的业务约束。”

“因此我们的 Agent 要输出证据，而不是一句简单的‘修复成功’。”

第八幕：Agent 为什么知道下一步要做什么？

故事进行到这里，林川产生了一个更深层次的问题。

“导师，Agent 怎么知道什么时候要搜索文件、什么时候运行测试、什么时候修改代码？”

陈工回答：

“这就是 Agent 编排机制。”

在普通 LLM 应用中：

用户提问 → LLM → 输出回答

而 Agent 是一个循环：

用户任务

LLM：判断下一步行动

根据当前任务状态与已有证据进行推理

工具执行

search / read / edit / test / git diff

观察结果

接收文件内容、构建日志或测试反馈

更新状态，再次决策

达到完成条件，或因限制停止

输出结果、证据和剩余风险

“这类模式通常与 ReAct 思想有关：Reasoning 与 Acting 相互交替。”

Agent 可能经历这样的决策过程：

Step 1:
  Action: search_code

“但这种循环不能无限运行。”

陈工提醒：

“如果模型一直找不到问题怎么办？如果它不断重复修改同一个文件怎么办？”

所以生产系统必须设置退出约束，比如最大工具调用次数、Token 预算、时间限制、连续失败次数和可恢复的检查点。

复杂场景下还可以使用显式状态机：

PENDING
   ↓
PREPARING
   ↓
LOCATING
   ↓
VERIFYING
   ↓
REPAIRING
   ↓
TESTING
   ↓
REVIEW_REQUIRED / COMPLETED

任意阶段可能进入：
FAILED / CANCELLED / TIMEOUT

“状态机负责确定流程边界，LLM 负责在授权范围内进行灵活推理。”

“如果缺少前者，Agent 可能陷入不可控的循环；如果缺少后者，整个系统就退化成普通的自动化脚本。”

第九幕：内网云端的秘密

林川又提出一个问题。

“为什么这套系统专门部署在公司内网云端？如果外部的大模型服务能力更强，我们直接调用外部 API 不行吗？”

陈工说：

“这涉及工程能力之外的另一个问题——企业代码安全。”

“代码仓库中可能包含业务逻辑、内部接口、未公开算法、数据库结构，甚至意外提交的凭证。”

“将这些内容发送给未经批准的外部服务，可能违反公司的安全要求。”

“但部署在内网，并不自动意味着安全。”

他列出几个关键风险：

风险 可能的问题 防护方案
仓库 URL 注入 访问内网敏感地址，形成 SSRF URL 协议和目标白名单、重定向校验、网络隔离
恶意仓库内容 README 中包含诱导 Agent 执行危险操作的指令 将仓库内容视为不可信数据、工具权限控制
构建脚本执行 pom.xml 插件或脚本执行恶意命令 隔离 Sandbox、资源限额、受控网络
越权修改 Agent 修改无关项目或敏感文件 仓库级 ACL、路径策略、最小权限
数据泄漏 源码、密钥进入日志或模型请求 脱敏、模型网关策略、数据边界
自动提交风险 错误补丁进入正式分支 独立分支、Pull Request、人工审批

林川问：

“如果 Agent 修改了错误的代码怎么办？”

“所以推荐它先在隔离分支里工作，生成 Diff，再由审核机制决定是否合并。”

“在默认情况下，修复权限不应该等同于直接发布生产环境的权限。”

这时，林川意识到了：

Coding Agent 的难点，不只是让 AI 有能力修改代码，更是让 AI 的修改行为可控、可验证、可追溯。

第十幕：导师的面试审判

下午，陈工突然关掉了投影仪。

“林川，假设你现在去参加一家公司的 AI 应用开发工程师面试。”

“面试官问：请介绍一下你的 Coding Agent 实习项目。”

“你会怎么回答？”

林川思考片刻。

“我实习做了一个 Coding Agent，用户输入 Git 仓库 URL、项目名称和 Bug 描述，系统利用大模型自动分析项目、检查 Bug 是否存在，如果存在就修改代码，再运行测试验证。”

陈工点头。

“这能让面试官理解业务功能，但还不足以体现工程深度。”

“他接下来一定可能追问这些问题。”

面试官第一问：如何证明 Bug 真的存在？

林川答：

“首先依据用户描述定位相关代码，结合项目中的业务约束与测试确认预期行为。对可复现的问题，优先构建最小失败用例，保存修改前的失败结果。然后修改代码，并再次执行相同测试，确认问题得到修复。”

陈工补充：

“还要考虑测试环境无法复现的情况，比如依赖缺失、业务数据不完整、并发条件难以模拟。此时应该明确输出无法验证及其原因，而不能强行认定 Bug 不存在。”

面试官第二问：Agent 和简单的 Prompt 调用有什么区别？

林川答：

“Agent 不只是一次性生成答案，而是能根据实际的代码搜索结果、文件内容、编译输出、测试日志动态决策。它通过工具调用与环境交互，形成多轮的推理—行动—观察循环。”

面试官第三问：项目代码非常多，超过上下文窗口怎么办？

林川答：

“采用渐进式代码检索，而不是加载整个仓库。先识别项目结构，再根据 Bug 描述进行关键词、符号和调用链检索，只读取相关代码。对于复杂任务可以逐步扩大分析范围，同时维护关键状态摘要，减少无关上下文。”

面试官第四问：如何保证 AI 不会乱改代码？

林川答：

“通过隔离环境、文件修改范围约束、Patch 审查、测试验证和独立分支管理降低风险。涉及关键业务或生产环境的变更，应设置人工审批。”

面试官第五问：测试通过，能否证明 Bug 已经修好？

林川答：

“不能完全证明。需要区分原 Bug 是否被复现、修复前后用例是否形成有效对照，以及是否引入了回归问题。测试通过只证明已覆盖场景符合预期，仍需评估未覆盖的边界情况。”

陈工听完，终于露出笑容。

“你现在介绍的不再只是一个接入大模型的功能，而是一个具备明确工程边界的自动化代码修复系统。”

尾声：真正的技术壁垒在哪里？

傍晚，林川独自回到工位。

他看着那套 Coding Agent 的执行日志。

他终于明白，自动化 Bug 修复表面上只是几个动作：

输入项目、检查问题、修改代码、执行测试。

但每一步背后，都有真正复杂的技术问题。

如何让 Agent 在百万行代码里准确定位问题？

如何让它识别用户描述中的错误假设？

如何让它在多次工具调用之后仍然保持正确的任务状态？

如何让它在有限的 Token、时间和计算资源中完成修复？

如何证明它修复的是根因，而不是单纯让测试通过？

如何让多个用户同时提交任务，而不会互相干扰？

以及最重要的：

如何把一个能演示的 Coding Agent，真正变成一个可以在企业生产研发流程中可靠运行的系统？

这些问题，将在下一章逐步展开。

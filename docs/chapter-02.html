阅读提示 · 把模型输出视为行动提议

模型提出工具调用，由 Runtime 校验名称、参数和授权后执行。示例中的循环应配合时间、Token 和工具次数预算；文本中的推理步骤是教学化决策摘要，并不意味着需要展示模型内部推理。

核心技术：ReAct · Function Calling · Tool Calling · Agent Loop · 状态机 · 上下文管理 · Java/Spring Boot 工程实践

第一章，林川见识了企业级 Coding Agent 的能力：用户输入项目地址、项目名称和 Bug 描述，系统便能尝试定位 Bug、验证 Bug、修复代码，最后运行测试。

但他始终有一个疑问：

大模型明明只是一个根据输入生成输出的程序，它凭什么能够操作整个代码仓库？又是谁在控制它下一步该做什么？

这一次，陈工决定带他进入 Coding Agent 的大脑。

第一幕：一场失控的自动修复

上午九点。

公司内网云平台突然响起一阵告警声。

林川打开监控大屏。

Task ID: agent-20261028-001
Project: payment-service

Task status: RUNNING

LLM calls: 86
Tool calls: 143
Elapsed time: 21m 32s

Current action: read_file
Target: src/main/java/PaymentService.java

林川揉了揉眼睛。

“143 次工具调用？一个 Bug 怎么会调用这么多次？”

他继续查看执行轨迹。

Step 81:  read_file(PaymentService.java)
Step 82:  search_code("payment timeout")
Step 83:  read_file(PaymentService.java)
Step 84:  search_code("retry")
Step 85:  read_file(PaymentService.java)
Step 86:  search_code("payment timeout")
...

“它好像一直在重复搜索同一段代码。”

陈工走到屏幕前。

“对，这就是典型的 Agent 失控循环。”

“但为什么？大模型不是很聪明吗？”

陈工没有回答，而是在白板上写下一段代码。

while (true) {
    String response = llm.chat(context);
    ToolCall toolCall = parseToolCall(response);

    Object result = execute(toolCall);
    context.add(result);
}

“看出来问题了吗？”

林川盯着代码。

“没有退出条件？”

“没错。”

陈工说：

“一个 Agent 如果只知道不断调用大模型、执行工具，却不知道什么时候该停止、什么时候该判断失败、什么时候应该切换策略，那它就不是一个可靠的智能体。”

“它只是一个无限循环的程序。”

“而这，就是今天我们要解决的第一个问题。”

第二幕：大模型本身不会执行任何工具

陈工打开一个 Java 项目。

“林川，你先告诉我，普通大模型是怎么工作的？”

林川回答：

“输入 Token 序列，经过 Transformer 计算，预测后续 Token。”

“那它能够直接打开本地文件吗？”

“不能。”

“能直接执行 mvn test 吗？”

“不能。”

“能直接修改 Git 仓库吗？”

“也不能。”

陈工点头。

“所以，当你看到一个 Coding Agent 能够搜索代码、读取文件、执行命令时，不要误以为这些操作是大模型自己完成的。”

真正执行操作的，是模型外部的程序。

LLM 与工具执行器的关系

LLM

判断下一步需要执行什么操作

输出结构化工具调用请求

Agent Runtime

校验参数、检查权限、路由工具、维护上下文

read_file

读取源码

search_code

检索代码

apply_patch

修改源码

run_tests

运行测试

执行结果重新进入模型上下文

陈工继续解释：

“假设模型认为应该读取 OrderService.java，它并不是直接打开这个文件，而是生成一个工具调用请求。”

例如：

{
  "name": "read_file",
  "arguments": {
    "path": "src/main/java/OrderService.java"
  }
}

“Agent Runtime 收到请求后，才会调用真正的文件读取程序。”

读取工具返回：

{
  "success": true,
  "content": "public class OrderService { ... }"
}

“然后 Runtime 再把工具执行结果交给模型，让模型决定下一步。”

林川恍然大悟。

“所以大模型相当于决策者，Agent Runtime 相当于执行机构。”

“基本正确。但别忘了，决策者也不能拥有无限权力。”

“Runtime 必须能够拒绝危险的工具调用。”

为什么 Function Calling 如此重要？

早期的一些 Agent 实现，会让模型生成自然语言命令：

我需要读取 OrderService.java，请运行以下命令：
cat src/main/java/OrderService.java

然后使用正则表达式提取命令。

陈工问：

“这种方式有什么问题？”

林川想了想。

“模型可能生成不符合预期格式的内容。”

“不止如此。它也可能把解释和命令混在一起，甚至生成危险的 shell 命令。”

现代 Function Calling 或 Tool Calling 机制通常允许开发者声明工具名称、描述和参数结构。

例如：

{
  "type": "function",
  "function": {
    "name": "read_file",
    "description": "读取当前任务工作区内的源代码文件",
    "parameters": {
      "type": "object",
      "properties": {
        "path": {
          "type": "string",
          "description": "工作区内的相对路径"
        }
      },
      "required": ["path"]
    }
  }
}

模型根据工具定义产生结构化调用，程序负责校验和执行。

不过陈工特别强调：

“结构化调用只是降低解析难度，不是安全保证。即使参数完全符合 JSON Schema，路径也可能指向不该读取的文件。”

因此还必须进行路径规范化、工作区边界检查、符号链接处理和授权校验。

第三幕：ReAct——让模型学会观察世界

下午，陈工给林川展示了另一套 Agent。

这套 Agent 不会一开始就生成完整修复方案。

它每次只决定接下来做什么，并依据实际结果继续行动。

“这就是一种经典的 Agent 思想：ReAct。”

ReAct 指的是将推理与行动相结合。

在工程实现中，我们通常把它组织为三个可观察环节：

判断下一步 → 执行工具 → 观察结果。

任务目标：修复订单重复创建问题

Reason / Decide

确定下一步需要什么证据

Act

调用代码搜索、文件读取或测试工具

Observe

接收真实文件内容或测试结果

根据新证据继续，直到满足终止条件

“我给你一个完整例子。”

用户提交任务：

项目 order-service 存在一个问题：重复提交订单时，可能创建多条相同订单，请确认并修复。

Agent 开始执行。

STEP 1

定位入口

模型选择调用 search_code("createOrder")。

Observation: 找到 OrderController.java 与 OrderService.java。

STEP 2

读取实现

模型调用 read_file("OrderService.java")。

Observation: 发现创建订单逻辑中缺少针对请求标识的幂等保护。

STEP 3

构建证据

生成针对性测试，并调用 run_tests()。

Observation: 测试失败，同一请求创建了两笔订单。

STEP 4

尝试修复

分析业务约束，生成最小补丁，执行 apply_patch()。

Observation: 修改成功，产生可审查的 Git Diff。

STEP 5

验证修复

重新执行针对性测试与必要的回归测试。

Observation: 测试通过，记录修复证据及未覆盖风险。

“这里最关键的是什么？”陈工问。

林川回答：

“每一步都不是预先完全写死的，而是可以根据上一轮的结果选择不同的行动。”

“没错。”

如果第三步测试没有失败，Agent 就不应该假装 Bug 已经复现。

它可能需要检查测试条件、查找相关配置或要求更多复现信息。

如果第五步测试失败，Agent 可以分析失败原因并尝试有限次数的修复，而不是立刻宣布成功。

这就是 Agent 和固定工作流的核心差异之一：它能够根据环境反馈动态决定局部行动。

但这并不意味着所有流程都应该由模型自由控制。

第四幕：Agent Loop——智能体真正的心脏

陈工打开 IDE。

“既然你已经理解了工具调用，我们现在自己实现一个最基础的 Agent Loop。”

他先定义一个模型决策结果：

public sealed interface AgentDecision
    permits ToolDecision, FinalDecision {
}

public record ToolDecision(
    String toolName,
    Map<String, Object> arguments
) implements AgentDecision {
}

public record FinalDecision(
    String answer
) implements AgentDecision {
}

“为什么要分成两种决策？”陈工问。

林川回答：

“一种表示模型还需要工具，一种表示模型认为任务结束。”

“是的。但还要注意，模型说结束，不意味着业务流程已经完成。”

陈工继续写下核心循环。

public AgentResult run(AgentTask task) {

    AgentContext context = initContext(task);

    for (int step = 0; step < MAX_STEPS; step++) {

        // 1. 向模型请求下一步决策
        AgentDecision decision = llm.decide(context);

        // 2. 模型请求结束
        if (decision instanceof FinalDecision finalDecision) {
            return validateAndFinish(
                context,
                finalDecision
            );
        }

        // 3. 模型请求执行工具
        ToolDecision toolDecision =
            (ToolDecision) decision;

        // 4. 校验工具名称、参数及权限
        Tool tool = registry.get(toolDecision.toolName());

        validateToolRequest(task, toolDecision);

        // 5. 执行工具，得到结果
        ToolResult result =
            tool.execute(toolDecision.arguments());

        // 6. 将结果加入任务上下文
        context.addToolResult(toolDecision, result);

        // 7. 更新状态并持久化检查点
        checkpointStore.save(context);
    }

    return AgentResult.limitExceeded(
        "Maximum tool steps reached"
    );
}

陈工关掉代码提示。

“这个循环虽然只有几十行，却包含了 Coding Agent 的核心框架。”

他在白板上写下：

St+1=F(St,At,Ot) S_{t+1}=F(S_t,A_t,O_t)

其中：

  • StS_t：当前 Agent 状态。
  • AtA_t：Agent 决定执行的动作。
  • OtO_t：工具执行后得到的观察结果。
  • FF：Runtime 对状态进行更新的逻辑。

模型负责给出候选动作，而整个系统由 Runtime 控制实际执行。

为什么不能完全相信模型的 Final Answer？

林川问：

“如果模型最终返回‘修复成功’，我们不就直接结束了吗？”

陈工摇头。

“模型可能在没有运行测试的情况下宣布修复成功。”

“所以最终必须有一个确定性的检查机制。”

例如：

private AgentResult validateAndFinish(
        AgentContext context,
        FinalDecision decision) {

    if (!context.hasVerifiedBug()) {
        return AgentResult.unverified(
            "Bug existence not verified"
        );
    }

    if (context.hasPatch()
            && !context.hasPassedRequiredTests()) {
        return AgentResult.reviewRequired(
            "Patch has not passed required tests"
        );
    }

    return AgentResult.reviewRequired(
        decision.answer()
    );
}

陈工解释：

“这只是示意代码。真实任务需要区分 Bug 不存在、Bug 未验证、已验证但无法修复、已修复待审核等多种终态。”

“不能让一个布尔值决定所有事情。”

这句话让林川记了很久。

模型可以建议任务结束，但是否满足完成标准，必须由系统根据可验证证据判断。

第五幕：Tool Registry——智能体的工具军械库

晚上，林川开始独立开发。

他遇到的第一个问题是：

“如果 Agent 需要十几种工具，难道每个工具都要写一段 if-else？”

if (toolName.equals("read_file")) {
    // ...
} else if (toolName.equals("search_code")) {
    // ...
} else if (toolName.equals("run_tests")) {
    // ...
}

陈工看了一眼代码。

“这可以跑，但是工具越来越多时，可扩展性会很差。”

“你可以把工具抽象成统一接口。”

public interface AgentTool {

    String name();

    String description();

    ToolResult execute(
        ToolContext context,
        Map<String, Object> arguments
    );
}

然后实现具体工具。

@Component
public class ReadFileTool implements AgentTool {

    @Override
    public String name() {
        return "read_file";
    }

    @Override
    public String description() {
        return "Read a file inside the task workspace";
    }

    @Override
    public ToolResult execute(
            ToolContext context,
            Map<String, Object> arguments) {

        String path = (String) arguments.get("path");

        Path file = context.workspace()
            .resolve(path)
            .normalize();

        // 这里只展示接口结构。
        // 实际实现需要校验越界、符号链接及文件权限。
        return context.fileService().read(file);
    }
}

之后通过 Spring 注入所有工具。

@Component
public class ToolRegistry {

    private final Map<String, AgentTool> tools;

    public ToolRegistry(List<AgentTool> toolList) {
        this.tools = toolList.stream()
            .collect(Collectors.toUnmodifiableMap(
                AgentTool::name,
                Function.identity()
            ));
    }

    public AgentTool get(String name) {
        AgentTool tool = tools.get(name);

        if (tool == null) {
            throw new IllegalArgumentException(
                "Unknown tool: " + name
            );
        }

        return tool;
    }
}

林川看到这里突然说道：

“这不就是策略模式加注册表模式吗？”

陈工点头。

“你可以这样理解。”

不同工具实现相同接口，Runtime 根据模型请求的工具名选择对应实现。

但一个成熟的 Tool Registry 还需要管理工具的参数 Schema、权限要求、超时时间、调用审计以及是否允许并行执行。

例如，有些工具只读：

read_file
search_code
list_directory
git_diff

有些工具会修改状态：

apply_patch
write_file
run_command
git_commit

后一类工具通常需要更严格的策略。

尤其是 run_command。

陈工严肃地说道：

“你一旦给模型一个不受限制的 Shell，就等于给了它在沙箱权限范围内执行任意命令的能力。”

“即使部署在内网，也必须对执行环境、文件系统、网络和资源使用进行限制。”

第六幕：Context Window——智能体的失忆症

第三天。

林川发现一个奇怪的现象。

在处理小型项目时，Agent 表现不错。

但面对一个大型 Java 微服务项目时，Agent 经常做到一半就忘记之前的分析结果。

它甚至会重复读取已经分析过的文件。

“为什么会这样？”

陈工回答：

“因为模型的上下文窗口不是无限的，而 Coding Agent 的执行过程会不断产生新内容。”

假设每次工具调用都向上下文增加大量日志。

Agent 上下文消耗示意

以下数值只是教学示例，并非实测数据。

035,00070,000105,000140,000任务开始搜索代码读取文件执行测试多轮修复

陈工说道：

“每次把完整测试日志、整个源文件、所有历史工具调用都塞进去，很容易让上下文迅速膨胀。”

“即使模型支持长上下文，也不代表所有信息都应该始终保留。”

林川问：

“那怎么解决？”

陈工在白板上写下三个词。

第一种：Sliding Window

只保留最近若干轮工具交互。

例如：

System Instructions
Task Goal
Essential State
Recent 10 Tool Interactions

优点是实现简单。

缺点是早期的重要证据可能被丢弃。

第二种：Context Summarization

对历史过程进行结构化压缩。

例如，原始历史中可能有几十次文件读取和测试执行。

将其压缩为：

Task: Fix duplicate order bug

Confirmed findings:
- OrderService.createOrder lacks request idempotency.
- Duplicate request test reproduced the bug.
- Related files: OrderService, OrderRepository.

Changes made:
- Added requestId handling.
- Added database uniqueness constraint.

Current status:
- Patch applied.
- Integration test has not yet completed.

Next action:
- Run database integration tests.

“这样既节约上下文，又保留重要证据。”

不过，陈工提醒：

“摘要本身也可能遗漏或误写信息，所以不能把摘要当成唯一的事实来源。”

关键事实应该来自持久化任务状态和原始执行记录。

第三种：外部状态存储

林川突然问：

“我们能不能把任务过程放在 Redis 或数据库里，而不是一直塞给模型？”

“当然。”

“而且这是企业级 Agent 非常重要的一部分。”

Agent Runtime

维护当前执行状态与下一步决策

数据库 / Redis

任务状态、检查点、租约、进度

Artifact Storage

完整日志、Diff、报告、测试结果

Context Builder

每轮只选择与当前决策相关的信息传给模型

“记住一件事。”

陈工说道：

Agent 的完整任务状态，不应该完全依赖 LLM Context 保存。

模型上下文用于决策，而外部状态存储用于记录任务事实、维护执行进度和恢复能力。

这两者不能混为一谈。

第七幕：任务状态机与恢复机制

这天夜里，公司内网云平台发生了一次短暂故障。

Agent 正在修改一个大型项目。

突然，Worker 进程崩溃了。

林川重新打开任务页面。

Task ID: agent-001
Status: RUNNING
Last Step: apply_patch
Worker: OFFLINE

“完了，Agent 的上下文全丢了。”

陈工说道：

“这就是为什么我们要设计 Checkpoint。”

“但如果已经执行了 apply_patch，进程恰好在记录成功之前崩溃呢？”

林川想了想。

“系统恢复后可能再次执行同一个 Patch。”

“没错，这属于经典的执行结果不确定问题。”

“在分布式系统里，不能简单地认为保存了任务状态，就拥有了 Exactly Once Execution。”

陈工设计了一个状态模型。

public enum TaskStatus {

    PENDING,

    PREPARING,

    LOCATING,

    VERIFYING,

    REPAIRING,

    TESTING,

    REVIEW_REQUIRED,

    COMPLETED,

    FAILED,

    CANCELLED
}

随后又增加了独立的步骤记录：

public record AgentStep(
    String stepId,
    String taskId,
    String toolName,
    String argumentsHash,
    String status,
    String artifactId
) {
}

每次执行工具之前先记录步骤意图。

执行完成后再保存结果与 Artifact。

对于可能重复执行的操作，则引入幂等性保护。

例如：

  • 文件读取可以安全重试。
  • 代码搜索通常可以安全重试。
  • apply_patch 需要检测补丁是否已经应用。
  • git_commit 需要核对提交记录，避免重复提交。
  • 对外部系统产生副作用的操作，则可能需要更加严格的确认和补偿机制。

陈工解释：

“恢复时不能只看数据库中的 RUNNING，还要判断实际工作区发生了什么。”

“你可以通过当前 Commit、工作区 Diff、工具执行记录、Artifact 等信息进行状态协调。”

林川问：

“是不是有点像分布式事务？”

“有相似的工程问题，例如幂等、故障恢复与副作用控制。但不要直接把 Agent Loop 等同于数据库事务。”

“因为一次 Agent 任务可能运行很久，还涉及文件系统、容器和外部工具，不适合用一个长事务把整个过程包起来。”

第八幕：无限循环与成本失控

第四天。

林川负责排查一条奇怪的告警。

Task: agent-002

LLM Requests: 158
Input Tokens: 1,820,000
Output Tokens: 125,000

Patch Attempts: 18
Test Failures: 18

Status: RUNNING

“它为什么还不停止？”

陈工回答：

“因为我们只给它规定了目标，却没有规定资源预算。”

他开始为 Agent 设计四类限制。

限制 示例值 防止的问题
最大决策轮数 40 轮 无限 Tool Loop
最大修复尝试 5 次 重复修改失败
最大执行时间 10 分钟 长时间占用资源
最大 Token 预算 200,000 成本失控

表中数字为示例值，生产环境应根据真实任务分布、模型成本和成功率进行调整。

但陈工并不满足于简单的计数限制。

“假设它没有达到最大轮数，却一直在读取同一个文件呢？”

“可以检测重复动作。”

“对。”

例如，记录最近若干步的工具名称、参数以及工作区状态。

如果连续多次执行相同工具调用，而没有产生新的信息，可以判断 Agent 陷入停滞。

但陈工进一步追问：

“如果它读的是同一个文件，但文件已经被修改了，还应该算重复吗？”

林川摇头。

“不应该。”

“所以不能只比较工具名和参数，还要结合文件版本、工具结果、任务进展。”

可以定义一个简化的进展信号：

Pt=f(new evidence,new tests,patch progress) P_t=f(\text{new evidence},\text{new tests},\text{patch progress})

当连续多个步骤没有实质进展时，Runtime 可以触发策略切换，例如要求模型重新规划，或终止任务并输出目前已经获得的证据。

对于不能准确量化的进展，优先使用明确规则，而不是伪造一个看似精确的“智能体进度分数”。

第九幕：Planner 与 Executor——一个大脑还是两个大脑？

第二周，林川开始处理更复杂的 Bug。

某个项目的修复需要同时检查 Controller、Service、Repository、数据库 Schema 和多个测试文件。

单一 Agent 不断在不同文件之间跳转，难以保持清晰的修复计划。

林川问：

“我们能不能让一个 Agent 负责规划，另一个 Agent 负责执行？”

陈工回答：

“可以。这是常见的 Planner-Executor 架构。”

用户 Bug 描述

Planner Agent

分析问题、拆分任务、规划验证步骤

定位订单创建链路

构建重复请求复现测试

修复幂等逻辑

运行回归测试

Executor Agent

实际调用代码工具、执行测试、报告结果

Verifier

独立检查补丁、测试和验收条件

“但我们为什么需要 Planner？”陈工反问。

林川回答：

“因为复杂任务需要拆解，避免 Agent 一直追逐局部线索，忘记整体目标。”

“对。”

不过他又补充：

“Planner-Executor 不一定比单 Agent 更好。”

“如果任务简单，多一个 Planner 就会增加模型调用成本与延迟。而且 Planner 自己也可能制定错误计划。”

“更合理的办法是根据任务复杂度选择架构。”

简单 Bug 可以使用单 Agent Loop。

复杂 Bug 可以使用 Planner-Executor。

跨多个仓库、多个模块的大型任务，才考虑引入更加复杂的多 Agent 协作。

Agent 数量不是越多越好，而是每个 Agent 是否承担了明确、可验证的职责。

第十幕：Java 工程中的完整串联

一天后，林川终于搭建出一个初步的 Spring Boot Agent 服务。

陈工要求他讲清楚：从前端点击“开始修复”，到底发生了什么？

林川打开设计图。

一次 Bug 修复任务的生命周期

1

Web 接入

接收仓库 URL、项目名、Bug 描述

2

任务服务

验证权限、创建 taskId、持久化任务

3

调度器

将任务分配给具备资源配额的 Worker

4

工作区管理

创建隔离工作区，获取固定版本的仓库

5

Agent Runtime

装载状态、构造 Prompt、调用模型

6

工具执行

搜索、读取、生成补丁、运行测试

7

状态与进度

记录 Step、Artifact、模型与工具执行轨迹

8

结果输出

生成 Diff、验证报告、风险说明，等待审核

“那你会如何设计核心 Java 服务？”陈工问。

林川写出了几个接口。

public interface AgentTaskService {

    String submitTask(CreateAgentTaskRequest request);

    AgentTaskStatus getStatus(String taskId);

    void cancelTask(String taskId);
}

public interface AgentOrchestrator {

    AgentResult execute(String taskId);
}

public interface ModelGateway {

    ModelResponse chat(
        List<ModelMessage> messages,
        List<ToolDefinition> tools
    );
}

public interface SandboxService {

    Workspace createWorkspace(String taskId);

    CommandResult execute(
        String workspaceId,
        CommandSpec command
    );

    void destroyWorkspace(String workspaceId);
}

这些接口构成了基本的职责分离。

AgentTaskService 管理用户任务。

AgentOrchestrator 负责 Agent 的整体生命周期。

ModelGateway 统一模型访问。

SandboxService 负责受控执行。

陈工指出：

“这只是一个可以继续扩展的工程骨架。”

“真正上线时，还需要任务租约、Worker 容错、幂等调度、分布式限流、模型调用重试、日志追踪、工作区清理以及权限审计。”

林川点头。

“我发现，一个看起来很简单的 Coding Agent，背后其实涉及 AI、后端、分布式系统和开发工具链。”

“这正是它真正有价值的地方。”

第十一幕：面试官的七连问

傍晚，陈工决定进行一场模拟面试。

“我们不讨论‘你用了什么框架’，而是讨论‘你是否真的理解这个系统’。”

七道核心面试题

展开全部

01为什么 Coding Agent 需要 Agent Loop，而不是调用一次 LLM？

因为代码修复依赖真实环境中的不确定信息。模型需要根据文件内容、搜索结果、测试输出不断调整行动。一次性生成补丁无法可靠处理这些反馈。

02Function Calling 是不是意味着模型可以直接执行函数？

03怎么防止 Agent 陷入无限循环？

04Agent 执行中途崩溃怎么办？

05为什么不能把所有代码都放到上下文里？

06Planner-Executor 一定优于单 Agent 吗？

07如何判断一个 Agent 真的完成了任务？

陈工收起题目。

“记住，对于你的实习项目，面试官真正关心的往往不是你能背多少 Agent 概念。”

“而是以下这些问题你能不能说清楚：哪些模块你真正实现过？为什么这样设计？遇到了什么故障？如何验证你做的改进？”

“如果你只负责过 Tool Calling，不要说自己设计了整个分布式调度系统。”

“如果没有做过 Sandbox，也不要把它描述成自己实现的安全隔离能力。”

“但你可以说明：从架构设计角度，如果系统需要进一步生产化，你会怎样补上这些能力。”

终章：Agent 的智能与工程的边界

深夜。

林川再次打开最初那个失控任务。

它曾经执行了 143 次工具调用，却始终无法完成修复。

而新的 Runtime 已经增加了任务预算、进展检测、状态检查点和退出机制。

当 Agent 反复尝试同一个修复方案时，系统不再允许它无限运行。

它会报告：

Task Status: REVIEW_REQUIRED

Bug:
  Reproduced

Root Cause:
  Suspected race condition in payment retry flow

Repair:
  Attempted 4 candidate patches

Verification:
  Required tests still failing

Reason for stop:
  Repair budget exhausted

Recommendation:
  Human investigation required

Artifacts:
  Reproduction test
  Candidate patches
  Test logs
  Execution trace

林川看着屏幕，突然问：

“导师，Agent 最终没修好 Bug，这算失败吗？”

陈工沉默片刻。

“从自动修复成功率来说，当然是一次没有成功完成的任务。”

“但是，从工程系统可靠性来说，它至少没有伪造成功，也没有无限消耗资源。”

“它留下了可以供人类继续调查的证据。”

林川终于明白：

一个成熟的 Coding Agent，不只是知道如何行动，还必须知道什么时候停止、如何承认不确定性，以及如何让人类接管。

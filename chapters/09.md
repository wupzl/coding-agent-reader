## 第一幕：面试官的第一句话

上午九点。

林川坐在一家大型 AI 公司的会议室里。

对面是一位有十多年后端与 AI 基础设施经验的面试官。

“先介绍一下你的实习项目。”

林川调整了一下呼吸。

“我参与的是一个部署在公司内网云端的 Coding Agent 项目。用户可以输入项目地址、项目名称，以及项目存在的 Bug 描述。”

“系统会获取项目代码，分析相关文件，判断 Bug 是否存在。如果确认问题，就尝试修改代码，并通过编译和测试验证修复效果。”

面试官点点头。

“听起来就是把代码发给大模型，让它生成补丁。”

林川没有急着反驳。

“模型生成补丁是其中一个环节，但完整的任务还涉及仓库上下文获取、工具调用、Bug 验证、修改范围约束、测试执行和任务状态管理。”

面试官问：

“那你们为什么需要 Agent？为什么不直接写一个固定工作流？”

林川想了想。

“因为不同 Bug 所需要的分析路径不同。”

“例如，编译错误可能通过静态分析和编译器输出定位；而并发 Bug 需要检查调用链、事务与数据库行为。”

“固定工作流可以定义总体阶段，但每个阶段内部需要根据实际证据动态决定下一步操作。”

面试官抬起头。

“所以，你认为 Agent 和 Workflow 的区别是什么？”

## 第二幕：Agent 和 Workflow，究竟有什么区别？

林川走到白板前。

他先画出普通 Workflow：

```text
获取仓库
   ↓
搜索代码
   ↓
调用模型
   ↓
修改代码
   ↓
运行测试
   ↓
输出结果
```

然后画出 Agent：

Workflow 与 Agent 的执行方式

固定 Workflow

读取代码

分析代码

生成补丁

运行测试

流程由程序预先定义

Agent Loop

模型判断下一步

调用工具

观察实际结果

继续决策或结束

林川解释：

“Workflow 的特点是步骤和状态转换主要由开发者预先定义。”

“Agent 则允许模型根据环境反馈动态选择工具和局部行动。”

“但它们不是完全对立的。”

面试官问：

“什么意思？”

“我们可以使用 Workflow 管理宏观阶段，例如仓库准备、Bug 验证、修复和最终审核。”

“在代码检索和修复阶段，使用 Agent Loop 动态决策。”

“也就是说，宏观流程确定，局部执行灵活。”

面试官终于点头。

“继续。”

林川补充：

“不是所有任务都值得使用 Agent。对于规则明确、输入输出确定的任务，固定工作流通常更可控，成本更低。”

“只有当任务需要反复获取未知信息，并且下一步行动依赖实际观察结果时，Agent 的价值才更明显。”

这是今天的第一个关键结论：

Agent 不是 Workflow 的替代品，而是一种能够嵌入 Workflow 的动态决策机制。

## 第三幕：不给框架，你能不能自己写一个 Agent？

面试官打开电脑。

“现在假设没有 LangGraph，没有任何现成 Agent 框架。”

“只有 Java 21、Spring Boot、一个支持 Tool Calling 的模型 API。”

“你能不能实现？”

林川回答：

“可以。我会先实现一个最小可用的 Agent Runtime。”

面试官问：

“从哪里开始？”

“先定义模型决策、工具注册和执行上下文。”

### 第一层：模型抽象

```java
public interface ModelClient {

    ModelDecision decide(
        AgentContext context,
        List<ToolSchema> availableTools
    );
}
```

模型返回两类决策。

```java
public sealed interface ModelDecision
    permits ToolCallDecision, FinalDecision {
}

public record ToolCallDecision(
    String toolCallId,
    String toolName,
    Map<String, Object> arguments
) implements ModelDecision {}

public record FinalDecision(
    String conclusion
) implements ModelDecision {}
```

面试官问：

“如果模型一次返回多个 Tool Call 怎么办？”

林川回答：

“可以将单个工具调用扩展为工具调用列表。但不能默认并行执行。”

“只读、相互独立的工具可以考虑并行；涉及文件修改、共享工作区或依赖顺序的操作，需要明确串行规则。”

“工具调用结果还必须按照协议与原始调用 ID 正确关联。”

### 第二层：工具接口

```java
public interface AgentTool {

    String name();

    ToolSchema schema();

    ToolResult execute(
        ToolContext context,
        Map<String, Object> arguments
    );
}
```

面试官问：

“Tool Registry 怎么实现？”

林川回答：

“通过 Spring 注入工具实现，建立工具名称到实现对象的映射。”

```java
@Component
public class ToolRegistry {

    private final Map<String, AgentTool> tools;

    public ToolRegistry(List<AgentTool> implementations) {
        this.tools = implementations.stream()
            .collect(Collectors.toUnmodifiableMap(
                AgentTool::name,
                Function.identity()
            ));
    }

    public AgentTool get(String name) {
        AgentTool tool = tools.get(name);

        if (tool == null) {
            throw new IllegalArgumentException(
                "Unknown tool: " + name
            );
        }

        return tool;
    }
}
```

“生产实现还会校验工具参数 Schema，并通过权限系统决定该任务能否调用指定工具。”

### 第三层：Agent Loop

林川写出了核心逻辑。

```java
public AgentResult run(AgentContext context) {

    for (int step = 0; step < MAX_STEPS; step++) {

        // 1. 检查取消、预算、任务租约
        runtimeGuard.check(context);

        // 2. 构造上下文并请求模型决策
        ModelDecision decision = modelClient.decide(
            context,
            toolRegistry.availableSchemas(context)
        );

        // 3. 处理模型结束请求
        if (decision instanceof FinalDecision finalDecision) {
            return completionValidator.validate(
                context,
                finalDecision
            );
        }

        ToolCallDecision call =
            (ToolCallDecision) decision;

        // 4. 校验工具调用权限
        authorizationService.check(context, call);

        // 5. 执行工具
        ToolResult result =
            toolExecutor.execute(context, call);

        // 6. 记录观察结果和 Checkpoint
        context.append(call, result);
        checkpointStore.save(context);
    }

    return AgentResult.budgetExceeded();
}
```

面试官盯着代码。

“这段代码有什么不足？”

林川回答：

“这是用于说明主要结构的简化实现。”

“真实系统需要处理模型 API 超时、工具执行超时、异常分类、上下文裁剪、多工具调用、并发冲突、Checkpoint 一致性，以及进程崩溃后尚未记录完成的工具副作用。”

面试官又问：

“最大步骤数到了怎么办？”

“停止自动执行，保留当前证据与修改 Artifact。如果存在未验证的补丁，不能宣布修复成功。”

面试官放下笔。

“不错。接下来是 Bug 验证。”

## 第四幕：你说能够判断 Bug 是否存在，怎么判断？

面试官拿出一条任务。

> 用户反馈：当库存只有一件商品时，两个用户同时购买，可能都下单成功。

“你们的 Agent 要怎么验证？”

林川回答：

“首先确认业务不变量：库存为 1 时，最多允许一个库存扣减操作成功。”

“然后通过代码检索定位库存扣减路径，检查是否存在读改写竞争。”

“如果发现可能的竞争条件，生成针对性的并发测试，在隔离环境中尝试复现。”

面试官问：

“假设运行一千次都没有复现呢？”

林川回答：

“不能直接判定 Bug 不存在。”

“可以检查测试是否真的覆盖到关键线程交错，数据库隔离级别是否与目标环境一致，以及是否存在锁、条件更新或乐观锁等保护机制。”

“如果仍然没有证据，可以输出 NOT_REPRODUCED 或 INCONCLUSIVE，而不是强行修改。”

面试官继续追问：

“模型能不能自己生成一个测试，然后自己判断测试正确？”

林川回答：

“可以生成候选测试，但关键验收条件应该由独立验证机制检查。”

“如果测试本身错误，Agent 可能把正确代码修改坏，或者通过降低断言要求获得虚假的成功。”

面试官问：

“那你如何证明修复有效？”

林川写下：

Bug 修复验证闭环

1

确定业务预期

明确正确行为与验收标准

2

原始版本复现

在 Base Commit 上触发对应缺陷

3

冻结验收证据

保存测试与环境记录，防止被修复过程篡改

4

应用候选 Patch

在干净工作区修改代码

5

重新验证

复现测试通过，执行必要回归检查

6

人工审核

检查根因、变更范围和剩余风险

面试官问：

“如果系统无法构建呢？”

“记录构建失败原因，并区分环境问题、依赖缺失和代码本身错误。”

“如果无法证明 Bug 存在，就不应声称已经验证完成。”

面试官点了点头。

“继续。”

## 第五幕：一百万行代码，Agent 如何定位 Bug？

面试官在白板上写下：

```text
项目：支付系统
代码规模：100 万行

Bug 描述：
支付接口偶尔超时，
但实际上已经扣款。
```

“你怎么定位？”

林川回答：

“我会采用渐进式检索。”

“首先识别项目结构和技术栈。”

“然后提取 Bug 描述中的业务实体和技术关键词，例如支付、超时、重试、支付网关。”

“先使用 Ripgrep 或符号搜索获取候选文件。”

“再通过 AST、LSP 或调用图沿 Controller、Service、RPC Client 追踪调用链。”

“如果自然语言和代码命名差异较大，可以使用 Code Embedding 做语义补充召回。”

面试官问：

“为什么不直接使用向量数据库？”

林川回答：

“因为向量检索擅长语义相似性，但并不能准确表示所有方法调用、类型关系和业务状态流转。”

“对于 Java 代码，符号解析和调用关系非常重要。”

“因此，词法检索、语义检索和结构化代码导航应根据任务特点组合使用。”

面试官问：

“找到了 `PaymentService.java`，是不是就成功了？”

“不是。问题可能发生在更底层的支付 HTTP Client 或重试逻辑中。”

“例如第一次支付实际成功，但响应超时，系统在没有稳定幂等键的情况下再次发起扣款请求。”

“所以需要结合实际日志、支付状态和渠道协议确认根因。”

面试官抬起头。

“你现在不是只在描述搜索技术，而是在解释软件系统的行为。”

## 第七幕：真实技术难点应该怎么讲？

陈工曾经告诉林川：

“面试官最容易识别的，不是你有没有记住术语，而是你能否解释一个问题从发现到解决的完整过程。”

面试官提出：

“请讲一个你真正遇到过的工程难点。”

对于这个问题，林川使用了一套结构。

工程难点表达模型：Problem → Diagnosis → Solution → Evidence

01

Problem

具体出现了什么现象，对业务或系统造成什么影响

02

Diagnosis

使用什么日志、Trace、测试或代码证据定位问题

03

Solution

为什么选择这一方案，有哪些替代方案与权衡

04

Evidence

如何验证问题解决，真实指标与剩余限制是什么

例如，在假设确实遇到过 Agent 工具循环的问题时，可以这样分析：

问题现象： Agent 在相同文件上重复执行 `read_file` 和 `search_code`，导致 Token 消耗增加，任务长时间无法结束。

原因定位： 检查执行 Trace，发现连续多轮没有产生新的代码证据，Runtime 又缺乏有效的终止条件。

解决方案： 添加最大步骤数、重复工具调用检测、任务预算，以及无进展时重新规划的机制。

验证方式： 构建固定测试任务，对比优化前后的重复调用数、Token 消耗、任务完成率及误终止情况。

面试官问：

“你实际做过这样的优化吗？”

林川回答：

“如果没有，我应该把它作为工程设计思路，而不是虚构为项目经历。”

这句话很重要。

因为真正的工程深度，不需要依赖编造经历。

## 第八幕：如果十万个 Bug 同时提交，怎么设计？

面试官关掉了 IDE。

“现在我们进入系统设计。”

“假设公司有一万名研发人员，短时间内提交十万个 Bug 修复任务。”

“你怎么设计整套平台？”

林川回答：

“首先，我会区分任务提交并发和实际 Agent 执行并发。”

“十万个任务可以进入队列，但不应该同时启动十万个 Sandbox。”

他画出架构。

大规模 Coding Agent 系统设计

Web / API Gateway

用户鉴权、项目授权、任务提交

Task Service + Database + Outbox

可靠创建、持久化与事件投递

Message Queue + Scheduler

削峰、优先级、租户配额和资源感知调度

Agent Worker 1

Agent Worker 2

Agent Worker N

Model Gateway

模型调用与 Token 配额

Sandbox Cluster

隔离代码执行与资源配额

Artifacts + Observability + Evaluation

Git Diff、测试报告、日志、Trace、实验评测

面试官问：

“系统最主要的瓶颈是什么？”

林川回答：

“不能预先断言只有一个瓶颈。”

“需要分别监控模型吞吐、Sandbox CPU 和内存、仓库下载、构建依赖、队列等待以及数据库状态更新。”

“不同阶段受不同资源约束。”

面试官问：

“怎么估算容量？”

林川写下 Little's Law：

\[ L=\lambda W \]

其中：

- \(L\)：系统内平均任务数量。
- \(\lambda\)：稳定条件下的平均任务完成吞吐。
- \(W\)：平均任务停留时间。

“如果要估算同时执行的任务数量，还需要区分排队时间和实际执行时间。”

“例如稳定状态下平均每秒完成两项任务，每个任务平均执行三分钟，则平均执行中的任务数量约为 360。”

“但这只是容量估算起点，还要考虑任务耗时分布、资源差异和长尾问题。”

面试官继续问：

“如果 Worker 崩溃，任务会不会重复执行？”

林川回答：

“消息可能重复投递，所以任务领取需要持久化状态、租约和执行代次。”

“恢复时检查已存在的工作区、Patch 和测试 Artifact，不能盲目从头执行可能有副作用的操作。”

面试官问：

“如果模型服务突然不可用？”

“模型网关应限制重试并提供故障降级策略。任务可以进入等待或可恢复失败状态，而不是让一千个 Worker 不断重试。”

面试官最后问：

“如果平台成本太高？”

林川回答：

“先通过 Trace 和评测判断成本来源，再考虑代码检索减少上下文、工具结果裁剪、仓库缓存、模型路由、阶段化资源调度和减少无效重试。”

“但不能只追求 Token 降低，而牺牲必要的验证步骤。”

## 第九幕：你这个项目到底有什么技术壁垒？

面试官忽然问：

“你觉得 Coding Agent 的技术壁垒在哪里？”

林川回答：

“如果只是把代码和 Bug 描述交给大模型，然后返回修改建议，技术壁垒相对有限。”

“但要把它建设成可靠的企业级系统，就会涉及多个困难问题。”

第一，代码上下文理解。

如何在大型仓库中定位与 Bug 相关的文件、调用链和业务约束。

第二，任务自主执行。

如何在工具执行反馈下动态规划，同时避免无限循环、状态丢失和资源失控。

第三，真实 Bug 验证。

如何构造可靠的复现条件，避免修复不存在的问题。

第四，代码修改与独立验证。

如何生成最小补丁、保护验收测试，并验证业务不变量。

第五，安全与云端工程。

如何让 Agent 在内网中受控执行不可信代码，并应对并发、崩溃、重复任务和资源争用。

第六，可靠评测。

如何证明 Agent 在陌生任务上确实提高了修复能力，而不是对固定数据集过拟合。

面试官问：

“这六个方向里面，哪一个最重要？”

林川回答：

“取决于产品定位。”

“如果是面向开发者的交互式 Coding Agent，代码理解、工具体验和修复质量可能更重要。”

“如果是企业内网的批量自动 Bug 修复平台，验证可信度、执行安全、权限管理与任务可靠性则更加关键。”

“没有一个脱离业务场景的绝对答案。”

面试官点了点头。

## 第十幕：项目介绍应该怎么讲，才能体现真实能力？

面试结束前，面试官给了林川最后一个机会。

“现在，请你重新介绍这个项目。”

这一次，林川不再从技术名词开始。

他先解释业务目标。

然后说明任务执行流程。

最后讲清楚工程挑战与个人贡献边界。

下面这是一份可以作为你自己项目介绍基础的版本。它只使用你已经明确提供的项目事实，不把前八章讨论过的参考架构都写成你真实实现过的功能。

我实习期间参与的是一个部署在公司内网云端的 Coding Agent 项目，主要面向项目代码中的 Bug 自动化分析、验证与修复场景。

从业务流程来看，用户可以输入项目地址、项目名称以及 Bug 的具体描述。系统会围绕指定项目进行代码分析，判断用户报告的问题是否存在。如果确认存在问题，则进一步尝试定位相关代码并进行修复，最后通过验证流程判断修复结果。

我认为这个项目与普通的 AI 问答系统相比，最大的区别在于它需要与真实代码工程环境交互。模型不仅要理解 Bug 描述，还要根据代码分析和工具执行结果逐步推进任务。

从工程设计角度，这类系统需要重点考虑几个问题：首先是如何准确定位相关代码；其次是如何通过测试或其他证据验证 Bug，而不是直接相信模型的判断；然后是如何控制代码修改范围、验证补丁，并处理工具执行失败、超时和任务状态恢复等情况。

此外，由于系统部署在公司内网云端，还需要考虑代码权限、数据安全与执行环境隔离。

在具体项目实现中，我主要参与的模块是【填写实际负责部分】。其中遇到的主要工程问题是【填写真实问题】，我通过【填写实际方案】进行了处理，并使用【填写真实测试或指标】验证效果。

这段实习让我对 Coding Agent 的认识从单纯的大模型调用，转向了模型决策、工具执行、代码环境与工程可靠性相结合的系统设计。

陈工曾经提醒过林川：

“面试项目时最容易出现的问题，是把自己知道的架构与自己实现过的工程混在一起。”

“真正可靠的表达，应该让面试官清楚区分三层。”

| 层次      | 应该讲什么              |
| ------- | ------------------ |
| 项目实际功能  | 系统已经具备哪些能力         |
| 本人实际贡献  | 自己负责的模块、问题和验证结果    |
| 设计理解与扩展 | 如果规模扩大或需要生产化，会如何设计 |

如果面试官进一步追问具体代码，就围绕真实实现回答，不应将参考方案说成现有系统的事实。

模型需要理解任务。

工具需要提供真实信息。

代码需要能够被定位。

Bug 需要证据证明。

补丁需要控制范围。

测试需要保证可信。

任务需要可靠执行。

权限需要受到约束。

效果需要独立评测。

他终于明白：

AI 工程的真正深度，并不只在于模型能生成什么，而在于我们如何把模型的不确定能力，转化成一个能够被验证、被控制、被维护的工程系统。
